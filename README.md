# 🚀 System_Part2 - 비동기 대규모 접속 채팅 서버

Rust의 `tokio` 비동기 런타임과 `broadcast` 채널을 활용한 고성능 멀티 클라이언트 채팅 서버 프로젝트입니다.  
500명 동시 접속 환경에서도 메시지 유실 및 중복 없이 안정적으로 동작하는 것을 목표로 합니다.

---

## 📁 프로젝트 구조

```
System_Part2/
├── src/
│   ├── main.rs        # 비동기 채팅 서버 (broadcast 기반)
│   ├── client.rs      # GUI 채팅 클라이언트 (Slint UI)
│   └── tester.rs      # 500명 동시 접속 무결성 검증 봇
├── Cargo.toml         # 프로젝트 설정 및 의존성
└── README.md
```

---

## 🛠️ 기술 스택

| 기술 | 용도 |
|------|------|
| **Rust** | 시스템 프로그래밍 언어 (메모리 안전성 보장) |
| **Tokio** | 비동기 런타임 (멀티스레드, 네트워크 I/O) |
| **broadcast channel** | 1:N 메시지 브로드캐스팅 |
| **Slint** | 크로스플랫폼 GUI 프레임워크 |
| **tokio::select!** | 다중 비동기 이벤트 동시 대기 |

## ⚙️ 실행 환경 요구사항

- **Rust**: 1.85+ (edition 2024)
- **OS**: Windows / Linux / macOS
- **네트워크**: localhost (127.0.0.1:8080)

## 🚀 실행 방법

### 1. 프로젝트 빌드

```bash
cargo build --release
```

### 2. 서버 실행

```bash
cargo run --bin System_Part2
```

서버가 정상적으로 실행되면 아래 메시지가 출력됩니다:
```
🚀 비동기 채팅 서버가 127.0.0.1:8080에서 실행 중입니다.
```

### 3. GUI 클라이언트 실행 (별도 터미널)

```bash
cargo run --bin client
```

> ⚠️ 클라이언트 실행 전 반드시 서버가 먼저 실행되어 있어야 합니다.

### 4. 대규모 접속 테스트 실행 (별도 터미널)

```bash
cargo run --bin tester
```

> 500명 동시 접속 테스트가 진행됩니다. OS 환경에 따라 파일 디스크립터 제한이 있을 수 있으므로,  
> 접속이 실패하면 `tester.rs`의 `CLIENT_COUNT`를 100~200으로 낮춰서 먼저 테스트하세요.

## 📝 각 파일 상세 설명

### `main.rs` — 비동기 채팅 서버

- `TcpListener`로 8080 포트에서 클라이언트 접속을 대기합니다.
- `broadcast::channel`을 생성하여 모든 클라이언트에게 메시지를 동시에 전달합니다.
- 각 클라이언트 접속 시 `tokio::spawn`으로 독립된 비동기 태스크를 생성합니다.
- `tokio::select!` 매크로를 사용하여 **메시지 수신**과 **메시지 브로드캐스트 전달**을 동시에 처리합니다.
- `RecvError::Lagged` 에러를 graceful하게 처리하여 메시지 폭주 시에도 서버가 중단되지 않습니다.

**핵심 동작 흐름:**
1. 클라이언트 접속 → `tx.clone()` + `tx.subscribe()`로 송수신기 할당
2. 클라이언트가 메시지 전송 → `tx.send()`로 방송
3. 다른 클라이언트의 `rx.recv()`가 메시지 수신 → 해당 소켓에 write

### `client.rs` — GUI 채팅 클라이언트

- **Slint** 프레임워크로 채팅 UI를 구성합니다 (입력창, 전송 버튼, 채팅 로그 영역).
- `TcpStream`을 `into_split()`으로 읽기/쓰기 분리하여 동시 처리합니다.
- `tokio::sync::mpsc` 채널로 GUI 이벤트와 네트워크 I/O를 연결합니다.
- **백그라운드 태스크 A**: 서버 → 클라이언트 (수신 전담, GUI 업데이트)
- **백그라운드 태스크 B**: 클라이언트 → 서버 (전송 전담)
- `slint::invoke_from_event_loop`으로 스레드 안전한 GUI 업데이트를 수행합니다.

### `tester.rs` — 대규모 접속 무결성 검증

- 500개의 비동기 봇을 `tokio::spawn`으로 동시 생성합니다.
- 각 봇은 고유한 메시지(`"Hello from Bot {id}"`)를 전송합니다.
- **`HashSet`**을 사용하여 수신한 메시지의 중복을 자동 제거하고, 고유 메시지 수를 카운트합니다.
- 모든 봇이 정확히 `CLIENT_COUNT`개의 서로 다른 메시지를 수신해야 테스트가 통과합니다.
- 2초 대기(`sleep`)로 모든 봇이 접속 완료된 후 동시에 메시지를 발송하여 Race Condition을 방지합니다.

## 🔑 핵심 설계 포인트

1. **OS 스레드 대신 비동기 태스크**: `tokio::spawn`은 OS 스레드가 아닌 경량 태스크를 생성하므로 수백~수천 개의 동시 접속을 효율적으로 처리합니다.

2. **Broadcast 채널**: 1개의 송신기(`tx`)에서 N개의 수신기(`rx`)로 메시지를 동시에 전달하는 1:N 패턴을 구현합니다.

3. **tokio::select!**: 여러 비동기 이벤트를 동시에 대기하며, 먼저 완료된 이벤트를 처리합니다. 이를 통해 읽기/쓰기를 하나의 루프에서 처리할 수 있습니다.

4. **HashSet 기반 무결성 검증**: 단순 카운터가 아닌 메시지 내용 자체를 저장하여, 중복 메시지가 도착해도 정확한 고유 메시지 수를 파악합니다.

5. **Lagged 에러 처리**: broadcast 채널의 버퍼(1024)가 가득 찼을 때 발생하는 `Lagged` 에러를 `continue`로 처리하여 프로그램 크래시를 방지합니다.

## 📌 참고사항

- Windows 환경에서 대규모 접속 테스트 시 기본 파일 디스크립터 제한에 걸릴 수 있습니다.
- Linux에서는 `ulimit -n 4096` 등으로 제한을 늘려주세요.
- Slint GUI 클라이언트는 별도의 바이너리로 빌드해야 합니다 (`Cargo.toml`에 `[[bin]]` 섹션 추가 필요).
