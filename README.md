# 🚀 System_Part2 - 비동기 대규모 접속 채팅 서버

Rust의 `tokio` 비동기 런타임과 `broadcast` 채널을 활용한 고성능 멀티 클라이언트 채팅 서버 프로젝트입니다.  
다수의 클라이언트가 동시에 접속하여 실시간으로 메시지를 주고받을 수 있으며, 봇 테스터를 통해 대규모 접속 환경을 시뮬레이션합니다.

---

## ⚙️ 실행 환경 요구사항

- **Rust**: 1.85+ (edition 2024)
- **OS**: Windows / Linux / macOS
- **네트워크**: localhost (127.0.0.1:8080)

## 🚀 실행 방법

### 1. 프로젝트 빌드

```bash
cargo build --release
```

### 2. 서버 실행 (둘 중 하나 선택)

**기본 서버** (main.rs):
```bash
cargo run
```

**로그 출력 서버** (server.rs) — 서버 터미널에 수신 메시지가 표시됨:
```bash
cargo run --bin server
```

서버가 정상적으로 실행되면 아래 메시지가 출력됩니다:
```
🚀 비동기 채팅 서버가 127.0.0.1:8080에서 실행 중입니다.
```

### 3. GUI 클라이언트 실행 (별도 터미널)

```bash
cargo run --bin client
```

- 메시지 입력 후 전송 버튼 클릭 또는 Enter 키로 전송
- 서버에서 브로드캐스트된 모든 메시지가 채팅 로그에 실시간 표시

> ⚠️ 클라이언트 실행 전 반드시 서버가 먼저 실행되어 있어야 합니다.

### 4. 봇 테스터 실행 (별도 터미널)

```bash
cargo run --bin tester
```

- 10개의 봇이 서버에 접속하여 인삿말(`"bot {id} hi"`)을 전송합니다.
- 이후 서버에서 브로드캐스트되는 모든 메시지를 실시간으로 출력합니다.
- client에서 메시지를 보내면 모든 봇이 해당 메시지를 수신하여 화면에 표시합니다.
- `Ctrl+C`로 종료합니다.

> 봇 수를 변경하려면 `tester.rs`의 `CLIENT_COUNT` 상수를 수정하세요.  
> OS 파일 디스크립터 제한에 걸릴 수 있으므로 대규모 테스트 시 주의가 필요합니다.

## 📝 각 파일 상세 설명

### `main.rs` — 채팅 서버 (기본 버전)

- `TcpListener`로 8080 포트에서 클라이언트 접속을 대기합니다.
- `broadcast::channel(1024)`을 생성하여 모든 클라이언트에게 메시지를 동시에 전달합니다.
- 각 클라이언트 접속 시 `tokio::spawn`으로 독립된 비동기 태스크를 생성합니다.
- `tokio::select!` 매크로를 사용하여 **메시지 수신**과 **메시지 브로드캐스트 전달**을 동시에 처리합니다.
- `RecvError::Lagged` 에러를 graceful하게 처리하여 메시지 폭주 시에도 서버가 중단되지 않습니다.

### `server.rs` — 채팅 서버 (로그 출력 버전)

- `main.rs`와 동일한 로직이지만, 서버 터미널에 수신된 메시지를 `📩 [LOG]` 형태로 출력합니다.
- 디버깅 및 모니터링 용도로 사용합니다.

### `client.rs` — GUI 채팅 클라이언트

- **Slint** 프레임워크로 채팅 UI를 구성합니다 (입력창, 전송 버튼, 스크롤 가능한 채팅 로그 영역).
- `TcpStream`을 `into_split()`으로 읽기/쓰기 분리하여 동시 처리합니다.
- `tokio::sync::mpsc` 채널로 GUI 이벤트와 네트워크 I/O를 연결합니다.
- **백그라운드 태스크 A**: 서버 → 클라이언트 (수신 전담, `invoke_from_event_loop`으로 GUI 업데이트)
- **백그라운드 태스크 B**: 클라이언트 → 서버 (전송 전담)
- 빈 메시지 전송을 방지하는 유효성 검사가 포함되어 있습니다.

### `tester.rs` — 대규모 접속 봇 테스터

- `CLIENT_COUNT`개의 비동기 봇을 `tokio::spawn`으로 동시 생성합니다.
- 각 봇은 접속 즉시 인삿말(`"bot {id} hi"`)을 전송합니다.
- 이후 서버에서 브로드캐스트되는 모든 메시지를 실시간으로 수신하여 터미널에 출력합니다.
- 10개 봇마다 50ms 간격을 두어 OS 파일 핸들 제한 문제를 방지합니다.
- 서버 연결이 끊기면 해당 봇은 자동 종료됩니다.

## 🔑 핵심 설계 포인트

1. **OS 스레드 대신 비동기 태스크**: `tokio::spawn`은 OS 스레드가 아닌 경량 태스크를 생성하므로 수백~수천 개의 동시 접속을 효율적으로 처리합니다.

2. **Broadcast 채널**: 1개의 송신기(`tx`)에서 N개의 수신기(`rx`)로 메시지를 동시에 전달하는 1:N 패턴을 구현합니다.

3. **tokio::select!**: 여러 비동기 이벤트를 동시에 대기하며, 먼저 완료된 이벤트를 처리합니다. 이를 통해 읽기/쓰기를 하나의 루프에서 처리할 수 있습니다.

4. **소켓 분리 (split)**: `TcpStream`을 읽기/쓰기로 분리하여 동시에 양방향 통신이 가능합니다.

5. **Lagged 에러 처리**: broadcast 채널의 버퍼(1024)가 가득 찼을 때 발생하는 `Lagged` 에러를 `continue`로 처리하여 프로그램 크래시를 방지합니다.

6. **점진적 접속 (Staggered Connection)**: 봇 테스터에서 10개마다 50ms 간격을 두어 OS 리소스 고갈을 방지합니다.

## 📌 참고사항

- Windows 환경에서 대규모 접속 테스트 시 기본 파일 디스크립터 제한에 걸릴 수 있습니다.
- Linux에서는 `ulimit -n 4096` 등으로 제한을 늘려주세요.
- `server.rs`와 `main.rs`는 동일 포트(8080)를 사용하므로 동시에 실행할 수 없습니다.
